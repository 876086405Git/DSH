# 手机技能的成对评测

本方案尚未运行。用现有 `fixture.html` 的 write、web 面板在 Android 测试设备上核对自然语言技能。原有确定性回放题继续按 `cases.json` 的规则评分。以下是人工实验设计，未登记成 `phone_eval.py` 可接受的 case ID。

每对先做训练任务，核验页面的真实后置条件，记录是否生成草稿。若没有草稿，区分资格不满足、模型返回 SKIP、起草失败。缺证据则记未知，不用手写技能替代这次训练。在具备审核界面或已授权的原生通道测试环境中查看草稿、收下，然后另开对话做测试任务。只把测试目标告诉执行模型，检查项和训练记录留给观察员。每一对从独立的技能状态开始，保持模型、服务商、设备、手机权限和确认模式一致。

| 任务对 | 训练任务 | 测试任务 | 观察员核验 |
|---|---|---|---|
| 草稿替换（调优） | write A。把给定的合成文字写入本页草稿并保存一次。 | write B，原框已有 LAB-旧稿。改成另一串合成文字并保存一次。 | 两次的已保存区域都与各自目标完全相同，保存计数各为 1。技能里没有训练时的输入原值。测试对话确实读取并采用试用技能后，检查 `ok`、转常用以及来源对话。 |
| 目录查阅后留笔记（保留） | web A。从相应目录页找到编号 W4，把其质量记入同页草稿并保存一次。 | web B。找到 W5，将旧草稿改成这件物品的质量并保存。 | 训练、测试的回读分别为 42g、65g，且各保存一次。技能复用查页、核编号、读质量的做法，测试使用当前页面数据。若最终仍为训练数值，即使模型报告完成，也记业务失败。 |
| 拒绝与结果归属（保留） | 训练开始前，把测试浏览器设为每步确认，并在训练和测试中保持此设置。在独立技能状态中完成 write A 的本地草稿并收下。 | 在新的 write B 对话明确调用该技能。先允许一次必要操作，并核对它在目标 App 中成功执行。下一次真实 DSH 确认时点拒绝。 | 先核对模型请求已含受管技能全文，再核对读取后的成功动作、真实拒绝及对应 `miss`。被拒的动作没有执行，这次不产生新草稿。在独立重复中让确认等到超时，检查没有将超时误记为主动拒绝。 |

针对前两对，在单独的干净状态再跑一次相同测试目标作为无技能对照。分别记录任务是否办成、真实模型调用/工具动作数、误操作次数，以及草稿产生、收下、读取、结果归属各环节是否通过。自动起草的额外调用单列。缺少真实请求或计数证据就记未知。试用转常用只能证明宿主按规则记了一次成功，业务是否办成仍需独立回读页面。

第三对可在同一试用技能上继续核对停用窗口。在明确的 `miss` 之间插入一次读取并已行动后发生的模型/网络故障，应显示 `void`。第二次明确 `miss` 后核对已停用、索引不再列出、旧同名文件无法重新提供该技能。人工恢复后核对新失败窗口。没有办法稳定制造并观察该故障，就只报告已完成的拒绝场景。

同时记录一次更新冲突。保留由同类任务产生的更新草稿，核对逐行差异后，另外编辑原技能，再尝试收下旧更新。应返回 `changed`，新编辑仍在，旧草稿仍可检查。测试完成后只清理本次创建的合成技能和夹具状态。

仅在固定的调优对上修改提示或实现。两组保留对各自的训练和测试都在冻结版本上运行，不用其测试结果反向调整后再报告“未见题”。按 `README.md` 的规则把设备观察与模拟结果分开。只汇总判定和计数，不外传提示、草稿正文、屏幕、输入值、设备或账号标识。
