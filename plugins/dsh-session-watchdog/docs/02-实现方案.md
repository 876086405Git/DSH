# 会话哨兵 · 实现方案

> 本文回答「怎么实现」：模块、数据结构、事件流、API 调用链、安装验证与风险。
> 「为什么这么设计」见 [01-设计说明.md](01-设计说明.md)。

## 1. 总体架构

~~~text
┌──────────────────────────── 宿主进程（Node，DSH profile）────────────────────────────┐
│                                                                                      │
│  session/event ──► detector(状态机) ──► policy(去重/预算/熔断) ──► feed(提醒事件流)      │
│        │                    │                                    │                   │
│        │                    └─ 断点事件缓冲(400 条) ──► context(提取 + 模板)            │
│        │                                                                              │
│        └─ turn/end/turn/start 驱动 ◄── runner ◄── 定时器(3s 后续跑)                    │
│                                              │                                        │
│                                  sessionController.prompt  ── 与 GUI 发消息同一条路径     │
│                                  agent.followup（兜底）                                  │
│                                                                                      │
│  store(原子写 JSON) ◄── 每事件/每 10s 持久化 ── 启动恢复(restore) + sessionQuery 扫描      │
│  webServer 路由：/config /alerts /action                                             │
└──────────────────────────────────────────┬───────────────────────────────────────────┘
                                           │ 浏览器轮询（1.5s，页面隐藏时 5s）
┌──────────────────────────────────────────▼───────────────────────────────────────────┐
│ 浏览器半侧（ModuleLoader 模块，lib/client.js）                                          │
│  轮询 /alerts → 右上角卡片（续跑/忽略） + 侧栏徽标 + 系统通知（Web Notification）           │
└──────────────────────────────────────────────────────────────────────────────────────┘
~~~

## 2. 模块清单

| 文件 | 职责 | 依赖 | 纯逻辑 |
|---|---|---|---|
| `lib/index.js` | 插件入口：订阅 `session/event`、编排判定/提醒/续跑、注册路由、启动恢复与扫描、持久化 | ctx 全服务（惰性） | 否 |
| `lib/detector.js` | turn 生命周期状态机；异常 kind 判定；假死心跳；工具调用宽限；审批等待；启动恢复播种 | 无 | 是 |
| `lib/policy.js` | 配置归一化；提醒/续跑决策；幂等去重；每会话/全局预算；连续失败熔断；状态序列化 | 无 | 是 |
| `lib/context.js` | 从事件流反向提取标题/目标/待办/最后用户与助手文本/最后工具/最后错误；**真实对话原文摘录** | 无 | 是 |
| `lib/resume-instruction.js` | **依据真实会话内容生成续跑指令**：llm 模式调模型、context 模式拼装、失败回落；交接简报与卡片摘要 | ctx.llm（惰性） | 部分 |
| `lib/runner.js` | 续跑投递：`sessionController.prompt(mode:'queue')` → 失败回落 `agent.followup`；`flush` 落盘确认 | ctx.sessionController / ctx.agents | 否 |
| `lib/notify.js` | 提醒事件流（cursor 增量）+ 3 条 webServer 路由 + 同源校验 | ctx.webServer（惰性） | 部分 |
| `lib/store.js` | 状态文件原子写（tmp+rename）、防抖、退出 flush | node:fs | 是 |
| `lib/config-store.js` | 运行时配置：白名单、原子写、覆盖合并；设置面板保存后即时生效 | node:fs / policy.js | 部分 |
| `lib/client.js` | 浏览器半侧：轮询提醒、卡片、徽标、系统通知、跳会话 | uiSession / uiWorkspace / Notification | 否 |

## 3. 关键数据结构

### 3.1 判定 Decision（detector 产出）

~~~ts
{
  id: string            // 幂等键 sessionId#turn#kind
  sessionId: string
  turn: number | null
  kind: 'completed'|'error'|'blocked'|'aborted'|'interrupted'|'max-tokens'|'forked'|'stalled'
  source: 'turn-end' | 'stall' | 'startup' | 'startup-scan'
  cancelCause: 'user'|'parent'|'hook'|'disposed'|'legacy'|null
  error: { message, code, status? } | null
  title, cwd, origin, awaitingUser
  at, savedAt?
}
~~~

### 3.2 提醒 Alert（feed 维护，浏览器可见）

~~~ts
{
  id, sessionId, title,
  kind, reason,                 // reason 为中文标签
  stage: 'detected'|'resuming'|'resumed'|'resume-failed'|'dismissed'|'superseded',
  error: string|null, turn: number|null, at: number,
  resumeAt: number|null, resumeCount: number, summary: string,
  cursor: number                // 递增游标，轮询增量用
}
~~~

### 3.3 状态文件 `~/.dsh/session-watchdog/state.json`

~~~jsonc
{
  "version": 1,
  "savedAt": 1762400000000,
  "detector": [{ "sessionId":"session-x", "openTurn":3, "lastEventAt":..., "title":"...", "cwd":"..." }],
  "policy": { "processed": [["session-x#3#error", 1762399999999]], "sessions": [["session-x", {"resumes":[...], "failures":0, "blocked":false}]], "globalResumes": [...] }
}
~~~

## 4. 事件流与时序

### 4.1 turn 结束（主通道）

> 时序注意：`turn/end` 在 `ReactLoopAgent.turn()` 的 `finally` 里同步 append，此时 `agent.status` 仍是 `running`（phase 要等 `kick()` 返回后才切 idle）。因此续跑决策**不读** `agent.status` 作为拦截条件；“用户已手动继续”只由后续 `turn/start` 事件撤销。

~~~text
turn/start{turn}                 detector: status=running, openTurn=turn, 清空工具/审批计数
tool/call / tool/result          detector: 维护未完成工具集合（假死宽限用）
assistant/message / user/message detector: 留存最后文本（续跑指令素材）
approval/asked|decided           detector: 维护 pendingApprovals（等人不算卡死）
turn/end{turn, reason}           detector: status=idle，产出 Decision
                                 policy.decide() → 提醒？续跑？
                                 extractContext + extractConversation（真实对话原文）
                                 feed.push(alert) → 浏览器轮询可见
                                 completed：提醒+铃声，不续跑
                                 异常且允许续跑：3s 后按最新内容生成指令 → runner.deliver()
~~~

### 4.2 假死心跳（每 15s）

`status==='running'` 且 `now - max(turnStartedAt, lastEventAt, 最新工具开始时间) > 阈值`：

- 无未完成工具：`stallTimeoutMs`（默认 10 分钟）
- 有未完成工具：`toolStallTimeoutMs`（默认 15 分钟，避免误伤长构建）
- 每个 turn 只报一次；默认只提醒不续跑（`resumeOnStall: false`）。

### 4.3 启动恢复（进程被杀）

- 插件每次事件/定时把「未闭合 turn」写进 state.json；
- 宿主重启后 `detector.restore(saved.detector, {savedAt})` 产出 `interrupted` 判定；
- 二次校验：若该会话其实有 live Agent 且仍在 running / 仍有未闭合 turn，则跳过；
- 要求 `savedAt` 距今 ≥ 10s，避免插件热重载误报。

### 4.4 启动扫描（插件首次安装的兜底）

`ctx.sessionQuery.listSessions()` 取最近 30 个「已持久化且未加载」的会话，`readSession()` 折出最后一条 turn 是否闭合；未闭合且最后事件在 24h 内 → 判定 `interrupted`（source=`startup-scan`）。

## 5. 续跑执行链路

~~~text
policy 判定可续跑（预算/熔断/awaitingUser/cwd 全过）
  → setTimeout(resumeDelayMs，默认 3s)
      ├─ 期间出现新 turn/start（用户手动继续）→ 撤销，stage=superseded
      └─ 到点 → runner.deliver(sessionId, promptText)
            ├─ 1) ctx.sessionController.prompt({requestId, sessionId, mode:'queue', content})  // 与 GUI 同路径，自动唤醒冷会话
            ├─ 2) 失败 → ctx.agents.get(id) / sessionController.resolveAgent(id) → agent.followup(手搓 UserMessage)
            └─ 3) await ctx.sessions.flush(agent.session)  // 落盘屏障
  → policy.recordResult(sessionId, ok)：成功清零失败计数，失败累计，达阈值熔断
  → feed.update(alertId, {stage})
~~~

### 续跑前的安全检查（全部在 policy/runner 内实现）

| 检查 | 行为 |
|---|---|
| 会话已被用户手动继续（新 turn/start） | 撤销续跑 |
| 等待用户审批（approval/asked 未 decided） | 只提醒 |
| 会话 cwd 不存在 | 只提醒 |
| 子代理会话（header.origin='subagent'） | 默认忽略 |
| 每会话预算（默认 2 次/30min） | 超限只提醒 |
| 全局预算（默认 5 次/10min） | 超限只提醒 |
| 连续失败（默认 3 次） | 熔断该会话 |
| 同一判定重复（sessionId#turn#kind） | 幂等忽略 |
| 启动恢复时 Agent 仍活着/仍有未闭合 turn | 跳过 |

## 5.5 设置面板链路

~~~text
设置页「会话哨兵」(settings.section 槽)
  ├─ 挂载：GET /dsh-session-watchdog/config → {config, defaults, editable}
  ├─ 编辑：提醒开关 / 监控内容规则 / 监控范围 / 阈值预算
  ├─ 保存：POST /config {patch:{仅改动字段}}
  │     → config-store.update(): 白名单过滤 → normalizeConfig 夹取 → 原子写 config.json
  │     → index.applyLiveConfig(): Object.assign(config, next) + detector.setOptions()
  │     → 返回最新全量；策略/心跳立刻按新值工作（无需重启）
  └─ 恢复默认：POST /config {reset:true} → 回到 cordis.patch.yml 的静态配置
~~~

优先级：`config.json` 覆盖 > `cordis.patch.yml` 静态 `config` > `DEFAULT_CONFIG`。写入路由同源校验（跨源 403）、未知字段 400、数值夹取。

### 5.6 任务完成提醒链路（v0.3）

~~~text
turn/end reason.kind === 'completed'
  → policy.decide(): notifyOnCompletion=true 时 notify=true、resume=false
  → index.handleDecision(): 摘要来自真实待办/错误（buildInstructionSummary）
  → feed.push(alert{kind:'completed', stage:'detected'})
  → 浏览器轮询拿到 alert：
      ├─ 卡片「任务完成」（只有「忽略」）
      ├─ 侧栏绿色完成徽标（30s 自清）
      ├─ document.hidden 且 notifyOs → 系统通知
      └─ completionSound !== 'none' → Web Audio 合成提示音（音量 completionVolume/100，同一 alert 只播一次）
~~~

提示音全部由 oscillator + gain 包络现场合成（零音频文件）：`dingdong` / `double` / `tritone` / `drop` / `chime` / `pulse`；设置面板可下拉选择、调音量、点「试听」。AudioContext 被自动播放策略挂起时只在首次交互后解锁，失败静默。

## 6. 浏览器半侧

- **模块形态**：`window.__ModuleLoader__.load({ id: 'dsh-session-watchdog', factory })`（CJS 惰性包装，不是 ESM；id 必须等于包名）。
- **状态源**：轮询宿主 `/alerts?since=<cursor>`（1.5s；`document.hidden` 时 5s），失败指数退避，最长 30s。
- **UI**：右上角卡片（最多 4 张，自动消失，可「续跑/忽略」）；侧栏 `sidebar.session.row.trailing` 徽标（红=异常、黄=续跑中、绿=已恢复）；点击徽标跳会话。
- **系统通知**：页面 `new Notification()`（Electron main 不可用，Host 是独立子进程；渲染进程受支持）。权限未授予先申请，被拒降级为仅页面卡片。
- **设置面板**：注册官方 `settings.section` 槽（`id=dsh-session-watchdog-settings`、`order=510`、`label=()=>'会话哨兵'`），四组表单：提醒开关 / 监控内容规则 / 监控范围（目录与会话 chip）/ 阈值预算；进入 GET 配置，保存只 POST 改动字段（秒↔毫秒换算在客户端完成），恢复默认需二次确认；slots/React 不可用时静默跳过。
- **宿主契约**：GET/POST `/dsh-session-watchdog/config`（读写配置）、GET `/alerts?since=`、POST `/action`（同源校验，跨源 403）。

### 8.1 启动扫描的安全默认

`source='startup-scan'` 的历史遗留判定默认只提醒（`resumeOnStartupScan: false`）；本插件自己状态文件恢复的 `source='startup'` 才默认续跑。首次安装不会突然唤醒一堆旧会话。

## 9. 已知限制与后续工作

- DSH 无 turn 级超时与 max-steps，本插件不擅自取消运行中的 turn（假死只提醒）。
- 第三方插件不能 import `@deepseek-ai/*`，因此上下文提取只基于事件流事实，不做模型摘要（可选 LLM 摘要留作后续）。
- 无「只记录不进模型」的会话内系统消息 API，提醒只能走 UI + 系统通知。
- 后续：配置面板、夜间免打扰、按工作区白名单、LLM 摘要开关、多实例去重（同一 profile 重复安装检测）。


## 10. v0.3.1 崩溃修复（2026-11-06 真机实测）

### 根因

v0.3.0 在「续跑」路径里直接读取了未声明的宿主服务：

```js
const instruction = await generateResumeInstruction({ llm: ctx.llm, ... })
```

本插件 `inject = []`，Cordis 对**未 inject 的服务属性读取**会抛
`CordisError: cannot get property "llm" without inject`。该异常发生在
`fire-and-forget` 的 `executeResume()` 里，没有任何 catch 接住，最终冒到宿主进程：

```text
dsh: fatal load failure: Error: cannot get property "llm" without inject
  at executeResume (profiles/desktop/node_modules/dsh-session-watchdog/lib/index.js:191)
  at onAction (...lib/index.js:288)
  at Object.handler (...lib/notify.js:191)
→ DesktopHostFatalError: cannot create effect on inactive context (dsh-desktop-host 二次崩溃)
```

触发条件：手动点「续跑」或自动续跑到点，**第一次真正执行续跑投递**时必崩（桌面端直接重启）。
崩溃日志：`%APPDATA%\@deepseek-ai\dsh-desktop\logs\crash-2026-11-06T06-32-40-056Z-host.log`。

### 修复

1. 新增 `readService(ctx, name)`：只用 `ctx.get(name)`（Cordis 不要求 inject），属性直读失败也吞掉；
   `ctx.llm / ctx.agents / ctx.sessions / ctx.sessionQuery` 全部改走该助手；
2. `executeResume()` 整体 try/catch，任何异常都降级为 `stage=resume-failed`，**绝不向外抛**；
3. 定时器与 HTTP action 的续跑调用统一走 `fireResume()`（Promise.resolve().catch 兜底），
   再也不会出现未捕获 rejection。

### 回归

- 新增严格上下文测试：模拟 Cordis 对未 inject 属性直读抛错的 Proxy，验证手动续跑返回 200、
  回落上下文模式并成功投递（`test/plugin.test.mjs`「插件未声明 inject 时直接读 ctx.llm 会崩宿主」）；
- 反向插桩 Mutation G：把代码改回 `ctx.llm` 写法 → 该测试必然失败（MUTANT_KILLED）。


## 11. v0.3.2 崩溃恢复上下文补读（真机自动续跑实测发现）

v0.3.1 上线后，桌面端真的又崩了一次（测试操作触发），这次崩溃反而给了**真实自动续跑**的证据：

- 提醒流出现 `kind=interrupted, stage=resumed, instructionSource=context`（session#9 的未闭合 turn）；
- 会话里真的多了一条插件投递的续跑消息，内容却是：

```text
【会话交接记录】
会话：（无标题）｜工作目录：F:\开发\Dsh-chajian
中断原因：进程中断｜宿主进程在 turn 未结束时退出
最近对话原文（从旧到新）：
  （没有可用的对话记录）
```

原因：宿主重启后 `detector.restore()` 只有状态快照，没有事件流；而续跑指令的真实内容来自事件缓存，
于是"承接上下文"退化成空记录（且 provider/model 也没记录到，只能回落 context 模式）。

修复（v0.3.2）：启动恢复判定前调用 `hydrateStartupDecision()`，用 `sessionQuery.readSession()`

## 13. v0.3.3 完成卡片摘要修复（CODE_RUN_FAILED 误导）

真机截图里正常完成的卡片出现了「正常完成 · CODE_RUN_FAILED」。`CODE_RUN_FAILED` 是
`@deepseek-ai/dsh-tool-executor-ptc` 在 **PTC 代码执行本身失败**时抛的 `HarnessError` 错误码
（见该包 `lib/index.js` 第 73/79 行），它来自会话日志里**最后一次失败的工具调用**，
**不是本轮 turn 的结束原因**（本轮 `turn/end.reason.kind = completed`）。

原因：`buildInstructionSummary()` 对任何 kind 都把 `context.lastError.code` 拼进摘要，
于是历史工具错误码被贴到「正常完成」卡片上。修复：

- `kind === 'completed'` 时摘要固定为「正常完成」，不再携带任何历史错误码；
- 只有异常停止（error/interrupted/max-tokens/blocked/stalled）才展示，并显式标注
  「最近工具失败 <code>」，避免歧义。

测试：新增「正常完成摘要不再携带历史工具错误码（避免 CODE_RUN_FAILED 误导）」；全量 63 pass。
